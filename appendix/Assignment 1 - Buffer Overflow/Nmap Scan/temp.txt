\begin{itemize}
\item{\textbf{Step 1: Inciting a crash}}
\begin{figure}[htb]
	\centering
	\includegraphics[width=\linewidth, margin=10pt]{img/buffer_overflow/vulns_counter/overflow.png}
	\caption{Visualization of Buffer Overflow exploitation procedure - Crashing the server}
	\label{stacks}
\end{figure}

To check if a Buffer Overflow is possible, an input consisting of repeating characters can be sent to the host system.
If the input is of sufficient size, and is not being validated correctly, the server will crash.
This happens, because writing the input to memory uncritically leads to the corruption of the return address (see \cref{stacks}, Step 1).
A string of repeating characters is not a valid address for the next instruction anymore, leading to a crash.
Inciting a crash this way indicates that a Buffer Overflow is present and could be exploited.

\item{\textbf{Step 2: Determining the offset}}\\
To determine how big the input needs to be to write to the EIP, the offset needs to be determined. Sending a non-repeating string of characters and inspecting, which characters get written to memory as bytes, allows the attacker to determine how long the input needs to be before the return address gets overwritten by the input (see \cref{unique_vis}).
\begin{figure}[!htb]
	\centering
	\includegraphics[width=0.6\linewidth]{img/buffer_overflow/vulns_counter/unique.png}
	\caption{Visualization of Buffer Overflow exploitation procedure - Offset determination}
	\label{unique_vis}
\end{figure}

\newpage
\item{\textbf{Step 3: Determining bad characters}}\\
For the injected code to be executed, the transmitted input including the payload needs to be processed by the host system. This could be prevented by bad characters, like the null byte or the carriage return.
To figure out which characters should be omitted in the final input, a string of all possible candidates can be sent to the host system, followed by an identifiable sequence of characters. Inspecting which characters show up in memory helps determine which characters should be omitted. If the identifiable sequence at the end shows up, no more bad characters remain.
\begin{figure}[!htb]
	\centering
	\includegraphics[width=0.6\linewidth, margin=5pt]{img/buffer_overflow/vulns_counter/bad.png}
	\caption{Visualization of Buffer Overflow exploitation procedure - Bad character determination}
	\label{bad_vis}
\end{figure}

\item{\textbf{Step 4: Determining the return address}}\\
To corrupt the return address properly, an advantageous address needs to be determined.
Since we elected to send a singular input containing the payload, we needed to find an instruction in memory which would force the host system to execute our payload after the function processing the input returns. On the Windows target machine, the JMP ESP assembly instruction was possible to be utilized. This instruction should be stored in non-randomized executable memory, to make use of the instruction possible and consistent.

\item{\textbf{Step 5: Executing the attack}}\\
The payload can now be transmitted, preceded in the input string by a string filling the buffer up to the return address, and the address that should overwrite the EIP (see \cref{attack_vis}).
\begin{figure}[!htb]
	\centering
	\includegraphics[width=0.6\linewidth, margin=10pt]{img/buffer_overflow/vulns_counter/attack.png}
	\caption{Visualization of Buffer Overflow exploitation procedure - Attack execution}
	\label{attack_vis}
\end{figure}\\
Care should be taken to provide the return address in the correct format.\\
Windows uses \enquote{Little Endian}, which may necessitate the byte order to be reversed.
\end{itemize}
