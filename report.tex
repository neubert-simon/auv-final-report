\paragraph{Scan Setup}
To achieve this, the following Nmap parameters were used:
\begin{figure}[h]
\makebox[1.05\linewidth][c]{%
	\includegraphics[width=1.1\linewidth]{buffer_overflow/nmap/flags}
}
	\vspace*{-5mm}
	\caption{Nmap - Configuration used to scan the target system}
\end{figure}\\
The parameters were chosen with the following reasoning \autocite{nmap}:
\vspace{-2mm}
\begin{itemize}
\item[-]{\textbf{T4}}\\
Sets the timing template. In this case, the second fastest scanning mode was chosen.
Since this scan happened in a laboratory setting, a stealthier (slower) option was not necessary.
\item[-]{\textbf{O}}\\
Enables OS detection, provides information about the target machine’s operating system.
\item[-]{\textbf{p-}}\\
Instructs Nmap to scan the complete port range to discover open ports on the target machine.
\item[-]{\textbf{sV}}\\
Instructs Nmap to scan for services and their versions on open ports.
\item[\texttt{--}]{\textbf{script}=\enquote{default, vuln}}\\
Executes the default non-intrusive general and vulnerability scripts during the scan. 
\item[-]{\textbf{Pn}}\\
This flag instructs Nmap to treat all hosts as online, skipping the ICMP ``ping" Nmap would otherwise perform before scanning the system.
It was known that the target was a Windows machine, which don't answer pings by default. Therefore, Nmap would assume the host was down if this flag weren’t set, ending the scan prematurely.
\item[-]{\textbf{v}}\\
Sets the output to ``verbose". This was chosen to see results immediately as they were found, enabling work on the already discovered information without having to wait for the whole scan to finish.
\item[-]{\textbf{oN} nmap.txt}\\
Writes the output to the file ``nmap.txt" in normal mode to record the scan results.
\item[-]{192.168.61.45}\\
The IP adress of the target machine that was to be scanned.
\end{itemize}

\begin{enumerate}
\item{\textbf{Port 445 - Windows 7 Enterprise 7601 Service Pack 1 microsoft ds}}\\
Nmap was able to identify the service running on port 445 as ``microsoft-ds".\\
The directory service (``ds") running here is common for port 445, implying that the SMB (Server Message Block) protocol is being used. \enquote{The SMB protocol is a network file sharing protocol. SMB allows you to read and write to files over the network on top of TCP/IP or other protocols} \autocite{microsoft:smb_feature_descriptions}.

\item{\textbf{Port 3389 - tcpwrapped}}\\
Nmap returning \enquote{tcpwrapped} means the TCP handshake was completed, but that the connection was closed by the host immediately without transmitting further data \autocite{venema1992tcp}. 
A service running on port 3389 usually is Microsoft's Remote Desktop Service \autocite{microsoft:rds_ports}.

\item{\textbf{Port 5555 - Service unrecognized}}\\
Nmap could not infer the service running on port 5555.
The closest fingerprint match it got is ``freeciv", a program that seems to be identified on port 5555 commonly by Nmap according to multiple user reports \autocite{samsepi0l:android4_vulnhub_writeup, nmap:issue1276, fahmifj:htb_explore_writeup}, even though it is not actually running on the port.

The two following lines returned by the service can be gathered from the fingerprint:\\
- \textit{``Hello There.\textbackslash r\textbackslash n"}\\
- \textit{``I break rules too!\textbackslash r\textbackslash n"}

All that can be gleamed from this scan result is that a service is running on port 5555 that returns text when called.

\end{enumerate}

\item[/]{\textbf{v}:192.168.61.45:3389}\\

\end{itemize}

\paragraph{Finding JMP ESP instruction}
To inject a payload carrying malicious code that creates a reverse shell, a reliable way of executing the reverse shell instructions was needed.
To instruct the host system to run the payload code, it must jump to the injected code and execute it.
Since the buffer is filled by the input sent to the target machine, and the ESP points to the top of the stack, the ESP will point to the injected code. Instruct the system to jump to the ESP would therefore lead to it executing the payload.
This can be achieved by writing the memory address of a JMP ESP instruction to the EIP, since it stores the address of the next instruction the system should execute after the current method returns.

First, the Opcode for JMP ESP needs to be determined.
The NASM shell, which shows opcodes for instructions on x86 systems \autocite{github:nasm_shell}, shows the JMP ESP opcode to be \textbf{0xFF 0xE4} (see \cref{4_jmp_esp_opcode}).

\begin{figure}[htb]
	\centering
	\includegraphics[height=3cm]{buffer_overflow/vulnServ/4_jmp_esp_opcode.png}
	\caption{Opcode determination}
	\label{4_jmp_esp_opcode}
\end{figure}

Now an address in memory storing this opcode could be searched for.
The first approach to find such an address would be to use the debuggers \enquote{Search for Command} feature in the thread that gets interrupted by attaching the debugger to the process.
The following memory address containing a JMP ESP instruction was found during the first search attempt (see \cref{jmp_found}):
\vspace{-2mm}
\begin{center}
	\setlength{\fboxsep}{6pt}
	\fbox{\large \textbf{0x 77 90 E8 71}}
\end{center}

\begin{figure}[!htb]
	\centering
	\includegraphics[width=1.054\linewidth]{buffer_overflow/pre_restart/jmp_found.png}
	\caption{Found JMP ESP instruction in the paused thread}
	\label{jmp_found}
\end{figure}

Upon restarting the target machine, this JMP ESP instruction was not located at the same memory address anymore. It was now stored at the following address (see \cref{jmp_found_post}):
\vspace{-2mm}
\begin{center}
	\setlength{\fboxsep}{6pt}
	\fbox{\large \textbf{0x 76 E4 E8 71}}
\end{center}

\begin{figure}[htb]

\subsection{Windows Scanning and Buffer Overflow}

\subsubsection{Vulnerability - Buffer Overflow} \label{subsubsec:buffer_overflow_expl}
To access the system initially, a Buffer Overflow vulnerability was used (see \fullref{subsec:buffer_overflow} for execution details).
The vulnerability can be classified as:\\
\textbf{CWE-120: Buffer Copy without Checking Size of Input ('Classic Buffer Overflow')} \autocite{mitre:cwe:120}\\
There is no CVE entry for the vulnerability in the VulnServer program, since it was specifically designed as an educational tool for Buffer Overflows \autocite{vulnserver}.

\paragraph{Working principle}
Cowan et al. explain the principle is, that a program vulnerable to Buffer Overflow does not validate input length or contents, instead writing the input to memory without proper bounds-checks. The attacker's goal is exploiting the fact that input isn't being validated correctly by the server, enabling them to overwrite memory with malicious code, taking over the program \autocite{cowan2000buffer}.

Cowan et al. continue that the program should be provided a string as input, which is made up of native CPU instructions. 
The program then writes this string to the buffer, storing the injected code. Since there are insufficient bounds-checks, the allotted buffer can be overstepped, writing to adjacent memory.
The exploit used intends to overwrite \textit{code pointers}, pointing to the instruction that should be executed next.
Cowan et al. go on to explain that the program lays down an Activation Record on the Stack for each function call, contain the return address, which point the operating system to the next instruction to run after the function has returned \autocite{cowan2000buffer}. 
In the case of the attacked Windows machine, this return address is held in the EIP register.
By corrupting this register with a suitable address, the attacker can force the target system to execute the injected code, which is called \enquote{The stack-smashing attack} \autocite{https://doi.org/10.1002/spe.515}.
The most common approach is to provide the vulnerable service with a string, that overflows the buffer, corrupts the return address and provides the payload right after \autocite{aleph:96}, which was utilized in this assignment.

\paragraph{Cause and Prevention of the vulnerability}
The VulnServer application cloneable from Bradshaw's Github repository uses \emph{strcpy} (see \cref{strcopy}), a C function which does not check if enough space is present before it copies input into the buffer \autocite{microsoft:strcpy}. 

\begin{figure}[!h]
	\centering
	\includegraphics[width=0.5\linewidth]{buffer_overflow/analysis/strcopy}
	\caption{Example of C Code vulnerable to Buffer Overflows from VulnServer Repo}
	\vspace{-2mm}
	\caption*{\small Source: \url{https://github.com/stephenbradshaw/vulnserver/blob/master/vulnserver.c}}
	\label{strcopy}
\end{figure}

Since the Buffer Overflow vulnerability is present, it can be assumed that the modified version of VulnServer deployed in the laboratory similarly does not conduct any bounds checks when processing the input.
To fix this vulnerability, a safer function like strcpy\_s could be used \autocite{microsoft:strcpy}, or a bounds check could be implemented before calling the unsafe function. In the latter case, the input length should be validated, ensuring it fits inside the allotted char buffer without flowing over.

\begin{itemize}
\itemIT{Application Isolation and Sandboxing (M10448)}
Segmenting and virtualization can help isolate compromised parts of the system. \autocite{mitre:attack:M1048}.\\
If the vulnerable application had been isolated more, it would be more difficult for an attacker to compromise the whole system even if they were to exploit the vulnerability.
\itemIT{Exploit Protection (M1050)}
Security applications monitoring the host system can detect malicious activity \autocite{mitre:attack:M1050}.\\
No SIEM, IDS, IPS or comparable system was in use in the laboratory, which should be employed in real environments.
\itemIT{Update Software (M1051)}
Performing regular software updates might patch possible vulnerabilities \autocite{mitre:attack:M1051}. The VulnServer application would not receive any updates, since it was deliberately designed to be flawed, but a real server application would likely receive regular patches during its lifetime.
\itemIT{Filter Network Traffic (M1037)}
Restricting outbound network traffic from publicly exposed servers can prevent connections to attackers \autocite{mitre:attack:M1037}. The reverse shell created during the assignment could be stopped if the appropriate packets were filtered out by a firewall.
\itemIT{Limit Access to Resource Over Network (M1035)}
Ensure all publicly exposed services are intended to be exposed \autocite{mitre:attack:M1035}.
It can be assumed that an actual server like the application running in the application would be intended to be exposed. Still, it could be useful to conduct checks on all publicly running applications, since other services might expose information or entry points into the network via other vulnerabilities inadvertendly.
\itemIT{Network Segmentation (M1030)}
Create a demilitarized zone (DMZ) to encapsulate public-facing services \autocite{mitre:attack:M1030}.
A DMZ could help encapsulate the compromised server, shielding it from the rest of the trusted network if it were deployed in a real environment. 
\itemIT{Privileged Account Management (M1026)}
Use the least privilege principle to limit exploitable permissions \autocite{mitre:attack:M1026}.
A real server should run with the least privileged user possible, to prevent compromised servers to immediately be able to access any part of the system.
\itemIT{Vulnerability Scanning (M1016)}
Periodically scan public-facing systems for vulnerabilities \autocite{mitre:attack:M1016}. If a vulnerability like the one in VulnServer were to be discovered in a real server, a regular scan could alert relevant personnel.
\end{itemize}

All listed mitigation strategies could reduce the risk of infiltration if the server were to be deployed outside the laboratory environment.

\subparagraph{Detection strategies}
\begin{itemize}
\item{\textbf{Exploit Public-Facing Application – multi-signal correlation (request → error → post-exploit process/egress)} (DET0080)}. \label{DET0080}
\end{itemize}
The following steps could be taken to detect Initial Access of this kind \autocite{mitre:attack:DET0080}:
\begin{enumerate}
\itemIT{Detect abnormal request patterns to the public endpoint}
Repeated connection attempts to the server with suspicious inputs could be flagged automatically.
\itemIT{Detect elevated 4xx / 5xx responses or invocations of unusual methods or paths}
Detecting repeated errors (crashing in the case of VulnServer) could indicate malicious requests.
\itemIT{Detect unusual instructions or loading of unusual modules}
Catching the invocation of unusual memory locations, like the JMP ESP command for example could indicate adversarial inputs.
\itemIT{Detect outbound callbacks}
The server should not be creating a reverse shell connection, detecting the outbound traffic could prevent attackers from utilizing their access.
\end{enumerate}
