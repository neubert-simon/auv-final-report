\paragraph{Reconnaissance (TA0043) \autocite{mitre:attack:TA0043}}

To gather information about the host system and possible vulnerabilities, an active scan was conducted via Nmap (see \fullref{subsec:Nmap_scan}).

\paragraph{Offensive techniques}

\begin{itemize}
\item{\textbf{Active Scanning} (T1595)}
\item{\textbf{Active Scanning: Vulnerability Scanning} (T1595.002)}
\end{itemize}
\vspace{-3mm}
An Active Scan is utilized to gather information about the target system for later use in an attack \autocite{mitre:attack:T1595} (open ports, services, the operating system, and possible vulnerabilities \autocite{mitre:attack:T1595/002}). The target was known, therefore it was not necessary to scan the whole laboratories IP range (Scanning IP Blocks [T1595.001] \autocite{mitre:attack:T1595/001}). Further scanning or reconnaissance was not necessitated by the assignment either. Since the attacking machine was able to tunnel into the laboratory network, scanning the machine directly was possible via network without any other setup. There were no mitigation tactics set up, therefore no tactics to stay covert were employed.

\paragraph{Defensive techniques} \label{subsec:TA0043-def}

\subparagraph{Mitigation Techniques}
\begin{itemize}
\item{\textbf{Pre-Compromise} (M1056)}
\end{itemize}
\vspace{-4mm}
Proactive measures can be taken to prevent a compromise.
Active scans are difficult to prevent, so the amount of sensitive data that is publicly accessible should be minimized, reducing the possible attack surface \autocite{mitre:attack:M1056}.

\subparagraph{Detection Techniques}
\begin{itemize}
\item{\textbf{Detection of Active Scanning} (DET0830)}
\item{\textbf{Detection of Vulnerability Scanning} (DET0867)}
\end{itemize}
\vspace{-3mm}
Both defensive techniques implore the system's administrator to monitor network traffic to detect anomalous behavior, for example port scanning. If suspicious traffic were to be detected, a firewall entry could be generated preventing the attacker from connecting to the target system. The act of Active Scanning itself does not necessarily need to be mitigated, in fact it cannot realistically be prevented when one is running public facing services. These strategies should be employed to monitor suspect behavior and act accordingly on subsequent connection attempts (for example blacklisting IPs that scanned the machine) \autocite{mitre:attack:DET0830, mitre:attack:DET0867}.

\subsubsection{Initial Access (TA0001) \autocite{mitre:attack:TA0001}}
\paragraph{Vulnerability}
See \fullref{subsubsec:buffer_overflow_expl}

\paragraph{Offensive techniques}
\vspace{1mm}
\begin{itemize}
\item{\textbf{Exploit Public-Facing Application} (T1190)}
\end{itemize}
\vspace{-5mm}
The attacker attempts to gain initial access via vulnerabilities in an outwardly exposed host or system \autocite{mitre:attack:T1190}.
In this case, the system was susceptible to an attack because unvalidated input is being written to memory without bounds-checking, enabling the Buffer Overflow.

\paragraph{Defensive techniques} \label{subsubsec:T1190-defenses}
The simplest way to prevent this attack would be input validation on the application level.
Checking that the authentication string and rejecting malformed inputs would help mitigation.

\subparagraph{Mitigation Strategies}
\begin{itemize}
\itemIT{Application Isolation and Sandboxing (M10448)}
Segmenting and virtualization can help isolate compromised parts of the system. \autocite{mitre:attack:M1048}.\\
If the vulnerable application had been isolated more, it would be more difficult for an attacker to compromise the whole system even if they were to exploit the vulnerability.
\itemIT{Exploit Protection (M1050)}
Security applications monitoring the host system can detect malicious activity \autocite{mitre:attack:M1050}.\\
No SIEM, IDS, IPS or comparable system was in use in the laboratory, which should be employed in real environments.
\itemIT{Update Software (M1051)}
Performing regular software updates might patch possible vulnerabilities \autocite{mitre:attack:M1051}. The VulnServer application would not receive any updates, since it was deliberately designed to be flawed, but a real server application would likely receive regular patches during its lifetime.
\itemIT{Filter Network Traffic (M1037)}
Restricting outbound network traffic from publicly exposed servers can prevent connections to attackers \autocite{mitre:attack:M1037}. The reverse shell created during the assignment could be stopped if the appropriate packets were filtered out by a firewall.
\itemIT{Limit Access to Resource Over Network (M1035)}
Ensure all publicly exposed services are intended to be exposed \autocite{mitre:attack:M1035}.
It can be assumed that an actual server like the application running in the application would be intended to be exposed. Still, it could be useful to conduct checks on all publicly running applications, since other services might expose information or entry points into the network via other vulnerabilities inadvertendly.
\itemIT{Network Segmentation (M1030)}
Create a demilitarized zone (DMZ) to encapsulate public-facing services \autocite{mitre:attack:M1030}.
A DMZ could help encapsulate the compromised server, shielding it from the rest of the trusted network if it were deployed in a real environment. 
\itemIT{Privileged Account Management (M1026)}
Use the least privilege principle to limit exploitable permissions \autocite{mitre:attack:M1026}.
A real server should run with the least privileged user possible, to prevent compromised servers to immediately be able to access any part of the system.
\itemIT{Vulnerability Scanning (M1016)}
Periodically scan public-facing systems for vulnerabilities \autocite{mitre:attack:M1016}. If a vulnerability like the one in VulnServer were to be discovered in a real server, a regular scan could alert relevant personnel.
\end{itemize}

All listed mitigation strategies could reduce the risk of infiltration if the server were to be deployed outside the laboratory environment.

\subparagraph{Detection strategies}
\begin{itemize}
\item{\textbf{Exploit Public-Facing Application – multi-signal correlation (request → error → post-exploit process/egress)} (DET0080)}. \label{DET0080}
\end{itemize}
The following steps could be taken to detect Initial Access of this kind \autocite{mitre:attack:DET0080}:
\begin{enumerate}
\itemIT{Detect abnormal request patterns to the public endpoint}
Repeated connection attempts to the server with suspicious inputs could be flagged automatically.
\itemIT{Detect elevated 4xx / 5xx responses or invocations of unusual methods or paths}
Detecting repeated errors (crashing in the case of VulnServer) could indicate malicious requests.
\itemIT{Detect unusual instructions or loading of unusual modules}
Catching the invocation of unusual memory locations, like the JMP ESP command for example could indicate adversarial inputs.
\itemIT{Detect outbound callbacks}
The server should not be creating a reverse shell connection, detecting the outbound traffic could prevent attackers from utilizing their access.
\end{enumerate} 

\subsubsection{Execution (TA0002)} \label{subsec:TA0002}
\paragraph{Vulnerability}
See \fullref{subsubsec:buffer_overflow_expl}

\paragraph{Offensive techniques}
\vspace{2mm}
\begin{itemize}
\item{\textbf{Exploitation for Client Execution} (T1203) \autocite{mitre:attack:T1203}}\\
\end{itemize}
\vspace{-11mm}
Software vulnerabilities in client applications lead to arbitrary execute code \autocite{mitre:attack:T1203}.\\
The attack in this assignment resulted in arbitrary code execution, compromising the system.

\paragraph{Defensive techniques}

\subparagraph{Mitigation Strategies}
If such a vulnerability is not possible to fix immediately, some of the same steps which were discussed in \fullref{subsubsec:T1190-defenses} can be taken to mitigate the exploitation of such vulnerabilities:
\begin{itemize}
\item{\textit{Application Isolation and Sandboxing (M10448)} \autocite{mitre:attack:M1048}}
\item{\textit{Exploit Protection (M1050)} \autocite{mitre:attack:M1050}}
\item{\textit{Update Software (M1051)} \autocite{mitre:attack:M1051}}
\end{itemize}

\subparagraph{Detection Strategies}
\begin{itemize}
\item{\textbf{Exploitation for Client Execution – cross-platform behavior chain (browser/Office/3rd-party apps)} (DET0287) \autocite{mitre:attack:DET0287}}
\end{itemize}
\vspace{-3mm}
Detection can be once again facilitated by observing a cause and effect chain \autocite{mitre:attack:DET0287}:
\vspace{-4mm}
\begin{enumerate}
\itemIT{A client app experiences a crash or abnormal exit / loads from an unusual location}
The server crashed because of the Buffer Overflow, which should raise red flags.
\itemIT{The app drops or modifies files}
Monitoring unexpected file access could help detect an attack, even though no files were modified during the attack in this assignment. 
\itemIT{The app spawns an unexpected child}
Creating a new powershell instance or an installer for example can be suspicious. The reverse shell connection was established directly via TCP during the attack in this assignment, therefore this technique wouldn't have worked as well here, but is still advisable to employ.
\itemIT{The app establishes an unusual outbound connection}
Looking out for unwanted connections can aid detection, see \fullref{DET0080}.
\end{enumerate}

\paragraph{Offensive techniques}
\vspace{2mm}
\begin{itemize}
\item{\textbf{Application Layer Protocol (T1071)}}
\end{itemize}
\vspace{-4mm}
Commands to the remote attacker system are sent via application layer protocols \autocite{mitre:attack:T1071}.\\
In this assignment, a TCP reverse shell was created via netcat, compromising the system.

\paragraph{Defensive techniques}

\subparagraph{Mitigation Strategies}

\begin{itemize}
\item{\textit{Filter Network Traffic (M1037)} \autocite{mitre:attack:M1037}} \\
See \fullref{subsubsec:T1190-defenses}
\itemIT{Network Intrusion Prevention (M1031)}
Intrusion prevention systems (IPS) could prevent attacks by identifying adversarial traffic and possibly thwarting exploitation attempts. \autocite{mitre:attack:M1031}
\end{itemize}

\subparagraph{Detection Strategies}
\begin{itemize}
\item{\textbf{Detection of Command and Control Over Application Layer Protocols} (DET0444)}\\
Detects suspicious usage of application-layer protocols via different metrics (e.g. byte count, ports etc.) \autocite{mitre:attack:DET0444}.
In the assignment the reverse shell connected to port 443 on the attacking machine, a port for which outbound traffic from a public server is highly unusual. 
\end{itemize}

Like was mentioned before, the laboratory environment didn't provide any implementation of these mitigation or detection tactics, from which a real life application would benefit.
